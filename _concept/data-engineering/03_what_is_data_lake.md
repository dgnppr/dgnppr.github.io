## 글을 쓰게 된 계기

데이터 레이크를 처음 접했을 때 특별한 기술이 있을 것이라고 생각했다. 그런데 실제로 구축된 것을 열어 보면 S3 버킷 하나에 파일이 쌓여 있는 것이 전부였다. 데이터 웨어하우스처럼 별도의 시스템이 돌아가는 것도 아니고, 설치할 소프트웨어가 있는 것도 아니었다.

그래서 한동안 데이터 레이크라는 말이 그냥 클라우드 스토리지에 붙인 이름이 아닌가 싶었다. 정리해 보니 절반은 맞고 절반은 틀렸다. 저장 자체는 실제로 폴더에 파일을 넣는 것에 가깝지만, 그 상태로는 아무도 질의할 수 없기 때문에 카탈로그와 쿼리 엔진이 얹혀야 비로소 쓸 수 있는 저장소가 된다.

이 글에서는 데이터 레이크가 무엇을 저장하는 곳인지, 그리고 그 위에 무엇을 더 올려야 질의가 가능해지는지 알아볼 것이다. 저장되는 파일의 형식 자체는 [앞 글](/concept/data-engineering/02_file_and_memory_formats)에서 다루었으므로 여기서는 그 파일들을 어떻게 배치하고 찾을 것인가에 집중한다.

<br><br><br>

## 데이터 레이크란 무엇인가

데이터 레이크는 원본에 가까운 데이터를 최소한으로 가공해서 그대로 보관하는 대규모 저장소다. 성격을 한마디로 말하면 규칙을 정해 놓고 쓰는 아주 큰 클라우드 폴더에 가깝다.

여기에 들어가는 데이터에는 제한이 거의 없다.

- 구조화 데이터: CSV, Parquet처럼 스키마가 분명한 표 형태의 데이터
- 반구조화 데이터: JSON, 로그, XML처럼 구조는 있지만 스키마가 고정되지 않은 데이터
- 비구조화 데이터: 이메일, 이미지, 오디오, PDF처럼 표로 만들 수 없는 데이터

데이터 웨어하우스와 비교하면 성격이 분명해진다. 웨어하우스는 데이터를 넣기 전에 스키마를 정하고 그에 맞게 변환해서 적재한다. 반면 데이터 레이크는 일단 원본을 그대로 저장하고, 읽는 시점에 그것을 어떻게 해석할지 정한다. 그래서 저장할 때는 형식을 강제하지 않지만, 그 대가로 읽는 쪽이 해석 책임을 진다.

이 방식이 유리한 경우가 있다. 지금 당장 쓰임새가 정해지지 않은 데이터를 일단 모아 두어야 할 때, 원본을 그대로 남겨서 나중에 다른 방식으로 다시 해석할 여지를 남겨야 할 때, 그리고 저장 비용을 낮게 유지해야 할 때다. 오브젝트 스토리지는 웨어하우스 스토리지보다 훨씬 싸기 때문에 일단 모아 두는 전략이 실제로 성립한다.

<br><br><br>

## 어떻게 구축하는가

구축 자체는 단순하다. Amazon S3나 [Google Cloud Storage](https://cloud.google.com/storage), [Azure Blob Storage](https://azure.microsoft.com/en-us/products/storage/blobs) 같은 오브젝트 스토리지에 버킷을 만들고 파일을 넣으면 된다. 여기서 실제로 결정해야 하는 것은 기술이 아니라 규칙이다.

### 명명과 파티션 규칙

경로를 어떻게 정할 것인지가 가장 중요한 결정이다. 이후의 성능과 운영이 대부분 여기서 갈린다.

```
s3://company-datalake/
  raw/                                  ← 원본 그대로
    orders/dt=2026-08-19/part-0001.parquet
    orders/dt=2026-08-19/part-0002.parquet
    orders/dt=2026-08-20/part-0001.parquet
  staging/                              ← 정제 중간 단계
  curated/                              ← 분석에 바로 쓰는 형태
    daily_sales/dt=2026-08-19/part-0000.parquet
```

`dt=2026-08-19` 형태로 디렉토리를 나누는 방식을 Hive 스타일 파티셔닝이라고 한다. 이렇게 두면 쿼리 엔진이 경로에서 `dt`라는 컬럼과 그 값을 인식하기 때문에, `WHERE dt = '2026-08-19'` 조건이 들어오면 해당 디렉토리만 읽고 나머지는 아예 열지 않는다. 파티션 프루닝이라고 부르는 동작이고, 읽는 데이터 양을 줄이는 가장 직접적인 수단이다.

파티션 컬럼은 대개 조회 조건으로 자주 쓰는 날짜를 기준으로 잡는다. 지역이나 서비스처럼 카디널리티가 낮으면서 필터에 자주 등장하는 컬럼을 한 단계 더 붙이기도 한다. 다만 너무 잘게 나누면 파일 하나가 지나치게 작아지므로 뒤에서 다시 언급할 문제가 생긴다.

원본, 정제 중간 단계, 분석용 결과를 계층으로 나누는 방식은 [메달리온 아키텍처](/concept/data-architect/00_what_is_medaliion_architecture)로 정리되어 있다.

### 접근 정책

레이크에는 성격이 다른 데이터가 한곳에 섞여 들어간다. 개인정보가 포함된 로그와 공개해도 되는 집계 결과가 같은 버킷 안에 있는 상황이 흔하다. 그래서 경로 단위로 권한을 나누는 설계가 필요하고, 이 설계는 명명 규칙과 함께 정해야 한다. 나중에 경로를 바꾸면 권한 정책도 같이 흔들리기 때문이다.

암호화, 버킷 버저닝, 그리고 오래된 데이터를 저비용 스토리지 클래스로 옮기는 수명 주기 정책도 이 단계에서 함께 정해 두는 편이 낫다.

### 관리형 선택지

직접 구성하는 대신 관리형 서비스를 쓸 수도 있다. Azure Data Lake Storage는 오브젝트 스토리지에 계층형 네임스페이스와 세밀한 권한 제어를 더한 형태이고, Snowflake도 외부 스테이지와 외부 테이블을 통해 레이크에 있는 파일을 직접 다루는 기능을 제공한다. 카탈로그와 권한 관리를 직접 운영하는 부담을 줄이는 대신 해당 생태계에 더 묶이게 된다.

<br><br><br>

## 데이터 늪이 되는 문제

데이터 레이크에서 가장 자주 언급되는 실패가 데이터 늪(data swamp)이다. 파일은 계속 쌓이는데 그 안에 무엇이 있는지 아무도 모르는 상태를 말한다.

원인은 대체로 비슷하다. 저장할 때 형식을 강제하지 않는다는 성질이 그대로 단점이 되는 것이다. 스키마가 기록되지 않은 채로 파일이 쌓이고, 같은 데이터가 경로만 다르게 여러 벌 생기고, 누가 언제 왜 넣었는지가 남지 않는다. 그러다 보면 어떤 파일이 최신인지, 어떤 것을 믿어야 하는지 판단할 근거가 사라진다.

여기서 중요한 점은 이것이 저장소의 문제가 아니라는 것이다. 오브젝트 스토리지는 요청받은 파일을 저장했을 뿐이다. 무엇이 어디에 어떤 스키마로 있는지를 기록하는 계층이 따로 없으면 생기는 문제이고, 그 계층이 다음에 볼 카탈로그다.

<br><br><br>

## 질의하려면 무엇이 더 필요한가

파일을 쌓아 두기만 하면 데이터를 쓰려는 사람이 경로를 직접 찾고, 파일을 내려받고, 형식을 파싱해야 한다. 이것을 하지 않고 SQL로 질의하려면 두 가지가 더 필요하다.

카탈로그는 테이블 이름, 스키마, 파티션 정보, 그리고 그 테이블이 실제로 어느 경로의 어떤 파일들에 대응하는지를 기록한다. 사람이 경로를 외우는 대신 테이블 이름을 쓸 수 있게 만들어 주는 계층이다.

쿼리 엔진은 카탈로그에서 그 정보를 읽어 어떤 파일을 열어야 하는지 판단하고, 필요한 파일만 읽어서 질의를 실행한다. 앞 글에서 본 Parquet의 footer 통계를 활용해 읽을 파일을 더 줄이는 것도 이 단계에서 일어난다.

두 계층이 붙으면 사용자 입장에서는 이런 흐름이 된다.

```
SELECT country, sum(amount)
FROM orders
WHERE dt = '2026-08-19'
GROUP BY 1

  ↓ 쿼리 엔진이 카탈로그에 orders가 무엇인지 묻는다
  ↓ 카탈로그가 답한다: s3://company-datalake/raw/orders/, Parquet, dt로 파티션됨
  ↓ 엔진이 dt=2026-08-19 디렉토리의 파일만 연다
  ↓ Parquet footer를 보고 country, amount 컬럼만 읽는다
```

사용자는 경로도 파일 형식도 몰라도 된다. 이 지점에서 폴더가 질의 가능한 저장소가 된다.

### 카탈로그 구현

Hive Metastore는 이 역할의 원형이다. 관계형 데이터베이스에 테이블 메타데이터를 저장하는 방식이고, 오래된 만큼 지원하는 엔진이 가장 넓다. 대신 직접 운영해야 하고 파티션이 아주 많아지면 병목이 되기도 한다.

[AWS Glue Data Catalog](https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html)는 Hive Metastore와 호환되는 관리형 카탈로그다. 크롤러를 돌려 경로를 훑고 스키마를 추론해 테이블을 자동 등록하는 기능이 있는데, 편리한 만큼 추론이 틀리면 잘못된 스키마가 그대로 등록되므로 중요한 테이블은 스키마를 명시하는 편이 안전하다.

[Unity Catalog](https://www.databricks.com/product/unity-catalog)는 Databricks가 만든 카탈로그로, 메타데이터 기록을 넘어 권한 관리와 데이터 계보 추적까지 함께 다루는 범위가 넓은 쪽이다.

### 쿼리 엔진

Apache Spark는 대규모 변환 작업에 강하다. SQL도 실행하지만 본래 성격은 분산 처리 프레임워크에 가깝고, 레이크에서 데이터를 읽어 정제하고 다시 쓰는 배치 파이프라인에 많이 쓴다.

[Trino](https://trino.io/)는 대화형 질의에 초점을 둔 분산 SQL 엔진이다. 중간 결과를 디스크에 쓰지 않고 메모리에서 처리해 응답이 빠르고, 여러 데이터 소스를 하나의 SQL로 조인할 수 있다는 점이 특징이다.

[Amazon Athena](https://aws.amazon.com/athena/)는 Trino 계열을 관리형으로 제공하는 서비스다. 클러스터를 띄울 필요 없이 S3를 바로 질의할 수 있고 스캔한 데이터 양으로 과금한다. 그래서 파티션 설계와 파일 형식 선택이 그대로 비용으로 나타난다. 같은 질의라도 CSV로 저장했을 때와 파티션이 잡힌 Parquet로 저장했을 때 스캔량이 크게 차이 난다.

<br><br><br>

## 카탈로그와 쿼리 엔진만으로는 남는 문제

여기까지 갖추면 파일 더미를 SQL로 질의할 수 있다. 다만 트랜잭션이 필요한 작업은 여전히 되지 않는다.

파일을 여러 개 쓰는 도중에 작업이 실패하면 반쯤 쓰인 상태가 그대로 조회에 노출되고, 두 작업이 같은 파티션을 동시에 덮어쓰면 한쪽이 조용히 사라진다. 행 하나를 지우려면 그 행이 들어 있는 파티션을 통째로 다시 써야 하고, 과거 시점의 상태를 다시 보는 것도 불가능하다.

이 문제를 풀기 위해 나온 것이 테이블 포맷이고, 데이터 레이크에 그 계층을 얹은 구성을 레이크하우스라고 부른다. 자세한 내용은 [테이블 포맷을 다룬 글](/concept/data-engineering/01_lakehouse_table_formats)에서 정리했다.

<br><br><br>

## 주의할 점

- 작은 파일이 쌓이면 성능이 무너진다. 파티션을 지나치게 잘게 나누거나 스트리밍으로 자주 쓰면 수 KB짜리 파일이 대량으로 생기는데, 오브젝트 스토리지는 파일 하나를 여는 비용이 적지 않아서 파일 수가 많아지면 그 비용이 데이터를 읽는 비용을 넘어선다. 주기적으로 작은 파일을 합치는 작업이 필요하다.
- 파티션 설계를 나중에 바꾸기 어렵다. 경로에 파티션 값이 박혀 있으므로 기준을 바꾸려면 데이터를 다시 배치해야 하고, 카탈로그 등록과 권한 정책도 함께 손봐야 한다. 처음에 정할 때 조회 패턴을 충분히 확인하는 편이 낫다.
- 카탈로그와 실제 파일이 어긋날 수 있다. 파이프라인이 파일만 쓰고 파티션 등록을 하지 않으면 데이터는 있는데 질의 결과에는 나오지 않는다. 반대로 파일을 지웠는데 카탈로그에 남아 있으면 질의가 실패한다. 두 곳을 함께 갱신하는 책임을 어디에 둘지 정해 두어야 한다.
- 스키마 추론에 의존하면 조용히 깨진다. 크롤러가 파일 일부만 보고 타입을 정하기 때문에 뒤에 예외적인 값이 들어오면 잘못된 타입으로 등록되고, 그 결과가 질의 시점에야 드러난다.
- 비용이 스캔량에서 발생한다. Athena처럼 스캔한 바이트로 과금하는 방식에서는 파티션 프루닝이 걸리지 않는 질의 하나가 큰 비용을 만든다. 조회 조건에 파티션 컬럼이 빠지는 경우를 막는 장치가 필요하다.
- 원본을 그대로 저장한다는 성질이 개인정보 관리와 충돌한다. 삭제 요청이 들어왔을 때 어느 파일에 그 데이터가 들어 있는지 추적할 수 없으면 대응이 불가능하다. 무엇을 어디에 넣는지 기록하는 일이 규정 대응의 전제가 된다.
- 저장이 싸다는 점이 그대로 함정이 되기도 한다. 비용이 낮으니 일단 쌓는다는 판단이 반복되면 관리되지 않는 데이터가 늘어나고, 결국 앞에서 본 늪 상태로 간다.

## 정리하면서

처음의 의문으로 돌아가면, 데이터 레이크가 클라우드 폴더에 가깝다는 인상은 저장 계층만 보면 맞는 말이었다. 오브젝트 스토리지에 규칙을 정해 파일을 넣는 것이 전부이기 때문이다.

다만 그 상태로는 데이터를 쓰려는 사람이 경로를 찾고 파일을 내려받아 직접 파싱해야 한다. 카탈로그가 테이블 이름과 스키마와 파일의 대응을 기록하고 쿼리 엔진이 그 정보로 필요한 파일만 읽어야 비로소 질의 가능한 저장소가 된다. 데이터 레이크를 구축한다는 말에서 실제로 결정해야 하는 것도 저장소 선택보다는 명명과 파티션 규칙, 접근 정책, 그리고 무엇을 기록으로 남길 것인가에 가깝다.

그리고 이 구성으로도 원자적인 쓰기나 행 단위 수정, 과거 시점 조회는 되지 않는다. 그 지점부터가 테이블 포맷과 레이크하우스의 영역이다.
